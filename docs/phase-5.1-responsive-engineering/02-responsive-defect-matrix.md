# 02 — Responsive defect matrix

**Session 5 update**: one new confirmed defect (really a recurring pattern, found 3 times), caught during continued English-locale deep visual review on the Portfolio listing page — a two-part heading (`<h2>{textA}<span>{textB}</span></h2>`) with no space between the two JSX expressions, so the rendered (and screen-reader-read) text runs the words together: "Plan forreal workflows", "Discussthe scope" (both on `/services`), and "Have a workflow to improve?Discuss" (on `/portfolio`'s closing CTA) — confirmed via `textContent`, not just visually. Same root cause, same fix (added the missing space in JSX) in all three places, in both locales (6 strings total). See [03-fixes-applied.md](03-fixes-applied.md) for the diffs. Other components using this two-part-heading pattern (`AboutSourceSections`, `MarketplaceFeaturesSection`, `ProductReasonsSection`, `PricingTable`, and the other usage in `PortfolioSourceSections`) were checked and already bake the needed space into the content string or a template literal — confirmed not affected.

**Session 3 update**: one new confirmed defect, found by extending deep visual review to the English locale for the first time (see row 4 below) — the home hero heading never scales down at any width in either locale, forcing up to 6 single-word lines in English. Found, fixed, verified cross-browser, and regression-guarded. Everything else re-verified clean under the brief's full 15-viewport matrix, applied this session to every content route and every portfolio project, not just home. Full account: [18-session-3-full-site-responsive-audit.md](18-session-3-full-site-responsive-audit.md).

**Session 2 update**: no new site defects were found. The two Session 1 fixes below were re-verified (automated, cross-browser) as still correct under much broader coverage — all 6 content routes × both locales × up to 15 viewports, all 9 portfolio projects × both locales, 3 browser engines. Several issues surfaced during Session 2's *own test-authoring* process (wrong assumptions, a browser-automation quirk, a cross-browser console-message wording difference) — none were site bugs; see [15-session-2-execution-report.md](15-session-2-execution-report.md) for the full account, kept separate from this matrix because they're about the test suite, not the site.

**Process note on fix 3:** the first version of this fix only reserved space in a `≤991.98px` media query (matching the vendor's own narrower mobile rule) and was verified correct there — but desktop (the vendor's *default*, unscoped rule) had no reservation at all and was never checked until a deliberate 1440px pass, which turned up a **worse** overlap than mobile ever had. The follow-up desktop fix then initially used an unscoped `!important` padding, which silently fought the vendor's existing mobile reduction and caused the heading to wrap into five cramped single-word lines at 375px — caught by re-screenshotting mobile immediately after the desktop change, not assumed safe. Both regressions were caught by re-verifying the *other* breakpoint after each change, not by reasoning about the CSS in isolation — the methodology takeaway is to always re-check the adjacent breakpoint(s) after any cascade-order (`!important`) fix, since `!important` does not respect `@media` scoping on its own.
