## Phase 1 and 1.1 implementation evidence

- Development seed data is under `db/dev-seeds/`; production migration discovery only sees numbered files under `db/migrations/`. The Docker runtime copies migrations only.
- Migration `0006_blog_lifecycle.sql` adds soft-delete timestamps, post revisions, and hashed idempotency keys. Soft-deleted slugs remain reserved.
- Admin create supports idempotency replay and payload mismatch rejection. Admin update requires an `If-Match` revision; restore is explicit.
- Public blog queries exclude trashed posts. Post create, edit, trash, restore, idempotency replay, and media-library flows are covered by the disposable admin Playwright suite. Targeted F-6 E2E also confirmed a trashed published slug changes from HTTP 200 to HTTP 404.
- Compose configuration validates for production with its host override and for Phase 4.3 staging using placeholder secret files. The exact-source migration image test above is local-only; production deployment was not performed.
- Production backup and restore scripts were exercised with a disposable GPG key, synthetic media, and PostgreSQL 17. The new manifest and backup-failure tests use command shims and synthetic fixtures. None were run against production paths, keys, containers, or data.
- Remaining release gates include the first-install rehearsal; production secret metadata verification; rollback compatibility; Path A definition/checklist; the host Nginx upload path and cache deletion propagation; complete historical-report supersession mapping; approval/merge of the pushed branch; an approved GPG key-custody and off-host backup destination/retention policy; and explicit production deployment authorization. No production deployment, migration, service restart, or production-data access was performed for this task.
