# Release and rollback runbook

> Production release record (2026-10-25): the Blog CMS was deployed from verified `main` commit `cebadd385648ee53a539888539e11a29aa211639`. The web and email-worker use `rakmyat-web:phase1-cebadd3` (`sha256:82f7ca3f28be3e0c5370b8a4efebc73f6a9ab484b9921f98afcee1832c7c6969`); PostgreSQL remains on 17.11 and migration `0006_blog_lifecycle.sql` is applied. The pre-deployment local backup and disposable restore-plus-migration rehearsal are recorded in `15-backup-and-recovery.md`. Bounded HTTPS smoke checks passed. Authenticated production CRUD/media testing remains pending an owner-controlled admin session.

For future releases, select an approved commit and build/tag the immutable image from that exact source. The release identifier `phase45-local-20261020-512c18c3` belongs to historical preparation and is not a commit or immutable production image.

1. Obtain the approvals in `19-owner-approval-gates.md`; confirm domain, host, DB, secrets, admin policy, monitoring and legal signoff.
2. Run production preflight; verify secret access and a timestamped, integrity-checked local database/media backup with a successful disposable restore rehearsal. For the initial release the owner accepts VPS-local unencrypted backups; GPG and off-host storage are not prerequisites. Do not echo environment or secret contents.
3. Build and scan the immutable candidate image. Validate Compose config; confirm only 80/443 are public and the database has no published ports.
4. Confirm migration review/restore plan, then run the one-shot migration only against the approved target.
5. Start services; verify DB/web/worker/edge health, TLS, English/Arabic public routes, contact without sending real inquiry, robots/sitemap gate, headers and admin authorization.
6. Monitor logs/alerts and inquiry/outbox state. Enable indexing only after separate owner approval.

Recovery after migration 0006 is forward-first: retain the migrated database and media, then fix and deploy a verified application image. Do not rely on image-only rollback to the prior production image; its source is unknown and prior local `main` can expose trashed published posts and has a different media path. If the database itself is damaged, restore the pre-deployment archive into a separate PostgreSQL 17 target, verify it, and apply migration 0006 there before considering cutover. The restore-plus-migration sequence passed on disposable tmpfs. Keep the original database and media directory intact until a replacement target is validated. The local backup is on the same VPS, so a host or disk failure is outside this release's recovery protection. Record who authorized each operation, timestamp, image digest, migration ID and outcome.

**Phase 1 rollback gate:** read-only comparison with the prior local `main` source at `6ce64a7882a5ebbe849d23008cffdc8576c4f60d` found that its public blog queries do not filter `deleted_at`, and its media upload route writes under `public/uploads`; Phase 1 stores media under the configured media root (production `/data/uploads`). An image-only rollback to that source after migration 0006 could expose trashed published posts and fail to serve media uploaded by Phase 1. Do not use that source as a rollback image until a compatibility release or an approved database/media recovery plan has been validated on disposable copies. The running production image is not source-traceable, so this inspection does not establish its behavior.

For the current media path, the application writes under `/data/uploads`. Production Compose uses a named volume; the VPS override binds the existing `/home/rakmyat/data/uploads` directory at that path. Preserve that host directory when changing the override. The upload handler accepts files up to 50 MiB and caps the multipart request at 51 MiB; Next.js `proxyClientMaxBodySize` and bundled Caddy `request_body` are set to 54 MiB. Host Nginx has a global 64 MiB request-body limit. HTTPS host-routed smoke requests reached the deployed web application; the authenticated `/api/admin/media` upload path through Nginx remains unverified. Nginx is host-managed and was not changed by Compose deployment.

Media URLs use random filenames and the application serving route emits `Cache-Control: public, max-age=31536000, immutable`. Deleting a file does not purge browser/CDN caches. The VPS Nginx `/uploads/` location currently sets a seven-day public cache instead; changing that host config or configuring CDN invalidation requires a separate operator-reviewed change. Prefer a cache purge when available; otherwise preserve versioned URLs and wait for the configured cache lifetime before assuming a deletion is no longer visible.
