# Backup and recovery

`scripts/production-backup.sh` streams a custom-format `pg_dump` directly into GPG encryption and verifies it with `pg_restore --list` inside the PostgreSQL container. It also creates an encrypted archive of regular files under `MEDIA_ROOT` (default `/home/rakmyat/data/uploads`) with a SHA-256 file manifest and file/byte counts. Empty media directories are valid and produce a manifest with zero entries. Verified artifacts are published without replacing existing names; failed temporary artifacts are marked `.FAILED`.

The optional encrypted workflow requires the matching GPG private key to be available in the operator's GPG keyring because it decrypts both archives for verification. The owner has explicitly approved local, unencrypted database and media backups on the VPS for the initial release. A GPG private key, external provider, off-host destination, and long-term retention system are not deployment prerequisites. Never echo secret contents.

For the initial release, the owner explicitly accepts a local, unencrypted pre-deployment snapshot on this VPS. On 2026-10-25 the snapshot was created at `/root/rakmyat-predeploy-20261025T194125Z` with a mode-0700 directory and mode-0600 files. It contains a PostgreSQL custom-format dump created by the installed PostgreSQL 17.11 tools (34,926 bytes) and a gzip tar of `/home/rakmyat/data/uploads` (316 bytes; zero regular files). SHA-256 checks passed, `pg_restore --list` succeeded, and both archives were restored into disposable tmpfs storage. The restored database then ran migration 0006 with the row count in `blog_posts` unchanged. This same-VPS snapshot does not protect against VPS or disk loss; off-host storage and GPG are not release prerequisites under the current owner decision.

`scripts/production-restore-drill.sh` requires a pre-created disposable target and refuses the production/default database names. It will not drop or create a database. `scripts/production-media-restore-drill.sh` requires a pre-created empty disposable directory and verifies the manifest, file count, total bytes, and SHA-256 checksums after extraction. Review and rehearse both scripts against disposable resources before relying on production backups.

The restore-drill scripts must never be run against production as a restore drill; they were run only against disposable targets. `production-backup.sh` remains the optional encrypted GPG workflow. The initial release's unencrypted local snapshot used a PostgreSQL custom archive and a tar media archive with explicit checksums and a successful disposable restore rehearsal. A local snapshot is a recovery point for application/database failures on this VPS, not a defense against VPS or disk loss. A local Phase 4.3 synthetic restore is documented in that phase's evidence.
